## 1. Intent

The owner downloaded free datasets from Kaggle (and Stooq) to `/media/thesix/ggTrader-data/market-data/`. The goal is to load them into the database so that **the existing research tools work on the new data**, with the daily stock bars "all combined": one place the tools read, whichever source a stock-day came from. Today the tools read only the `yfinance` / `1d` rows of `public.ohlcv` through `ggTrader.data.bars.load_bars` (see the "Database map" in `AGENTS.md`).

Why now: the all-stocks research phase needs prices for stocks that no longer trade and for years before 2000. The current tape has 1,443 symbols from 2000 to 2026. The Kaggle copy of CRSP (68.9 million daily rows, 25,754 stocks, 1968 to 2024) is the first free source with that coverage. Including stocks that later died is a goal where the data allows, not a rule on a source.

## 2. Goals, non-goals, anti-goals

Goals
- Every file in section 5 ends up in the database, traceable to its SHA-256 in the download folder.
- `load_bars` (and so the lab, walk-forward runs and studies) reads CRSP-derived history through the same call, and the source of each day is knowable.
- Every load is a dated, append-only version, in the manner of the `universe` schema.
- A failed or interrupted load can never look like data.

Non-goals (version one)
- Delisting returns, a complete PERMNO-to-ticker map (SEC and CUSIP matching), a Shumway-style fill for dead stocks: each is its own later study.
- Changing the paper trader or any live path (the trader stays stopped), or the engine.
- Importing the Stooq or Quandl OHLCV files (the design must not rule them out; they carry open, high, low and volume).
- Running any strategy test on the new data.

Anti-goals (a failure even if it loads)
- Rows that look like real tickers but are guesses; an identity table that looks complete when it is 13% complete.
- Silent dropping or repair of bad rows.
- The live database filling its disk, or existing tools returning different numbers for stocks they already read.

## 3. Constraints

- **Disk.** The database is 14 GB on the main drive (455 GB, about 152 GB free on 2026-11-22; the 75 GB measured earlier was stale, so re-measure before every load). The stored size of the new data is **not established**; earlier "20 GB final, 54 GB peak" figures were guesses. A rough uncompressed allowance from row counts is 16 GB for the CRSP rows, derived bars and SEC facts plus 3 GB for the 94 GKX characteristics, before indexes, temporary files, the write-ahead log (the database's crash-recovery journal) and compression workspace. The two big CRSP tables and the 82.2 million SEC facts are therefore compressed hypertables (or carry no secondary index until needed). **Measure first:** the builder loads one representative year of each large table with its indexes, compresses it, then **reloads that same year as a second version** (the real peak is old rows, new rows, indexes and compression workspace together in an already compressed year), and projects full size and reload peak against the free space then available. The full load starts only if the projected peak leaves at least **40 GB free** (default; the owner may change it). Chunks are sized by row count and date range, not by Parquet row group (row group 0 alone spans 1968 to 2024). **Retention:** a reload keeps the previous load until the owner approves deleting it; at most two loads per dataset are kept, and a third needs the owner's say, so the budget always counts every retained version. A load a readable release depends on is never deleted (6.5). Free space is checked before every chunk. **Amended 2026-11-22 (build ruling):** the CRSP file is read in its own 66 row groups, and every row group spans 1968 to 2024, so chunks cannot be one per year; the loader writes row-group chunks and compresses after the last chunk. The measured uncompressed peak for the full CRSP table is about 10.3 GB (pilot, results/kaggle_pilot/pilot-2026-11-22.json: 149 bytes a row uncompressed, 32 compressed). The owner chose the main drive for speed; a larger drive is coming.
- **Backup.** No scheduled backup of `ggtrader` exists (Docker volumes and `~/ggtraderdb` are excluded from the system backup). A one-off full dump was taken on 2026-11-22 to `/media/thesix/ggTrader-data/ggtraderdb-backup-20261122/` (9,699,410,184 bytes, SHA-256 recorded, archive listing read successfully). A restore into a scratch database has **not** been run. The first load does not start until the owner accepts this backup or asks for the restore drill, and the importer checks that a dump no older than **7 days** exists (default; the owner may change it).
- **Time.** `ohlcv.timestamp` is `timestamp without time zone` holding naive UTC midnight. Never write a tz-aware value (the 2026-08-20 day-shift disaster). No new `timestamp without time zone` columns elsewhere: use `date` or `timestamptz`.
- **`load_bars` guarantees.** It raises on a duplicate `(timestamp, symbol)`, a non-midnight stamp or a weekend. Any source it reads must satisfy that.
- **Chunks.** `ohlcv` uses 7-day chunks; 56 years of daily bars would add about 2,900 chunks to the present 1,402.
- **Writers.** Research code reads the database read-only (`load_bars` opens a read-only session). The importer is the only writer and is a separate, explicit command.
- **Project rules.** Ruff-clean, type hints, `argparse` and `--help` on every script, long jobs resumable, tests only through `scripts/run_tests.sh` on small targets.

## 4. Approach chosen

Three shapes were considered: (A) one generic importer driven by a manifest file, (B) a separate loader script per dataset, (C) load everything untouched and derive clean data through views. **Chosen: B's code with A's contract, borrowing C's rule.** One command, `ggt db import <dataset>`, backed by one shared library (SHA-256 check against the download list, free-space guard, chunked `COPY`, row-count and sample checks, load record). Each dataset is a short Python module with hooks for its quirks (negative prices, garbage dates, a 3.8 GB CSV, a column named `end`). Each source is stored **as delivered** (CRSP keeps its negative-price sign) and cleaned forms are derived from it.

## 6. Combining the daily bars

### 6.0 Words used in this section

- **Stock:** a company's share class as CRSP numbers it (a PERMNO), which never changes, unlike a ticker.
- **Spell:** one unbroken stretch of trading data for a stock (rule in 6.1). A stock has one spell unless its data has a break.
- **Link:** the recorded finding that a `yfinance` symbol and a CRSP stock are the same company (6.3).
- **Splice:** joining a linked stock's older CRSP prices to its newer Yahoo prices into one series (6.4).
- **Release:** one published, numbered set of compatible loads, links and settings, so a run can say exactly what it read (6.5).
- **Hypertable:** a TimescaleDB table that the database splits into time chunks (and can compress) automatically.
- **Provenance:** the record a run keeps of exactly what it read and with which code, so two results can be compared fairly.
- **Fingerprint:** a short code computed from data, which changes if the data changes.
- **Plain-SQL function that pushes filters down:** a stored query the database can run efficiently by reading only the symbols and dates asked for.
- **OD7:** the project's name for the optional forced-exit rule for stocks whose data has ended.
- **Close rescaled:** the CRSP-derived `close` is scaled so its day-to-day changes are right; its dollar level is not what the stock traded at.

### 6.1 Identity, spells and symbols

- Every CRSP stock becomes readable by the tools, including the roughly 22,000 with no known ticker. **Owner decision: a stock without a ticker gets the placeholder symbol `PERMNO-<permno>`.**
- **A stock is its CRSP number, not its ticker.** `load_bars` reshapes rows into one column per symbol, so a stock whose symbol changes mid-history would be cut into several "stocks", and two companies that used one ticker would be glued into one. This is real: in the McGill file 354 stocks change ticker and 179 tickers belong to more than one stock; `ohlcv` holds Meta as `META` from 2012 while CRSP and McGill call it `FB` until 2022; `ohlcv` has `PX` and `LIN`, and `VIAC` and `PARA`, as separate symbols.
- **Version-one symbol rule.** A linked stock uses its `yfinance` symbol, and the link only adds earlier CRSP days to that existing Yahoo column. Every other stock uses `PERMNO-<n>`. McGill tickers and return-match links are recorded in `ref.symbol_map(permno, symbol, valid_from, valid_to, source, release_id)` but are **not** used as column names; the table records only what a source proves. A request returns exactly the symbol asked for. A requested symbol that does not exist in the release (for example `PERMNO-84761` for a stock whose column is `TTWO`, or a `~k` that is not there) is listed in `missing_symbols`, never an error and never an alias.
- **Why historical tickers are not translated in version one.** `load_bars` takes one date window for all symbols, so it cannot say "`FB` means Meta before 2022 and something else after" (`ohlcv` already holds a live `FB`, a different security from 2025-06-26); `VIAC` (193 rows) and `PARA` (1,929 rows) both start 2019-03-04, so aliasing one to the other would give `load_bars(["VIAC"])` a column named `PARA`; and the S&P membership list names stocks by their ticker of the day, so its mask would have to follow a renamed column. Translation and the membership rule are version two.
- **Two companies with one ticker** (old and new GM) are two stocks in two columns. The Yahoo `GM` column links to the new company; the old company stays `PERMNO-<n>`. The link test refuses a link that would attach one company's Yahoo history to another's CRSP history. The clash is counted in the load record.
- **Spells: when a return is real.** CRSP's uploader deleted rows whose return was a letter code (`B`, `C`). The first row kept after a missing session carries a return measured against a **deleted** row, so it is the return from a price the file no longer shows. Two examples, both checked against the raw file: stock 10066 stops 1990-01-29 at $0.047 and shows $3.56 on 1999-03-19 (raw has a deleted 1999-03-18 row at $3.94, so its -9.5% is real but cannot be chained from 1990); stock 10128 has no price from 1986-04-14 to 04-21, a deleted `C` row at $3.125 on 04-22, and a kept row on 04-23 at $2.875 with return -8% (the move from $3.125), though the last kept price was $4.625 on 04-11.
  **Rule.** A row whose previous session is present is always chained (this is why splits never cut a stock). A row after one or more missing sessions starts a **new spell and has no return**, unless **all** of these hold: the gap is 10 sessions or fewer (on the file's own 14,347-session calendar); the shares figure is present and non-zero on both sides; and the **market value** (absolute price times shares) change across the gap agrees with the row's reported return within a tolerance (2 percentage points to start, calibrated). When all hold, the row is chained and **its return is the market-value change across the gap, not the reported return**, flagged "gap return approximated from price" (the reported return is measured from the deleted row, so it is not the holder's return). Stock 10669 shows why: its last kept price is $18.25 on 1987-04-24, the deleted `C` row on 05-07 is $18.00, and the kept 05-08 row is $18.00 with a reported return of 0%; the holder's real move was -1.37%, which is inside the tolerance, so using the reported 0% would have been wrong. Measured on the whole file: 21,024 retained rows follow a missing session. Of the 18,234 with 1 to 10 missing sessions, 214 disagree by more than 2 points on market value and 34 have zero or missing shares, so **248 start a new spell**; all 2,790 rows after longer gaps start a new spell. An earlier draft cut at every price-versus-return disagreement, which cut IBM, AAPL and MSFT at every split; the rule above applies the test only after a missing session. Acceptance tests: 10066, 10124, 10128 and 10669, and IBM, AAPL and MSFT (not cut at splits).
  A gap in the data is not always a trading halt or delisting (SMCI's 2018-2020 gap and IBKR's 2018-2019 gap are exchange moves outside the file's exchange codes while Yahoo traded throughout), so spells are never reported as delistings.
- **Which spell carries which name (rewritten after the Comverse, Take-Two, Super Micro and Visteon traces).** For a linked stock, `first_yf_date` is the first day of its `yfinance` rows. The scale (6.4) is taken on the first day on or after `first_yf_date`, within 5 sessions, on which both CRSP and Yahoo have a row; a one-day hole inside a spell therefore does not block a splice. An unlinked stock has no `first_yf_date`.

  | Case | Column and rows |
  | :--- | :--- |
  | Unlinked stock | The latest spell is `PERMNO-<n>`; earlier spells are `PERMNO-<n>~1` (oldest), `~2`, and so on. |
  | Linked stock, a spell whose dates span `first_yf_date` and has a common day within 5 sessions | That spell's rows **before** `first_yf_date`, scaled, are the early part of the Yahoo symbol's column; Yahoo supplies `first_yf_date` and every later day. |
  | Linked stock, spells that end before `first_yf_date` | `PERMNO-<n>~k`, oldest first. |
  | Linked stock, every CRSP row on or after `first_yf_date` | Not readable under any name (no company counted twice). |
  | Linked stock with no spell spanning `first_yf_date` (Visteon), or whose first CRSP row is up to one session after Yahoo's first day (Super Micro, Interactive Brokers) | No splice. The Yahoo symbol is Yahoo only; spells that ended before `first_yf_date` keep `~k`; later CRSP rows stay hidden. |

  **Visteon (88319), line by line.** Old CRSP spell (to 2009-03-05, $0.02) is `PERMNO-88319~1`; `VC` is Yahoo only from 2010-10-05; the CRSP spell from 2011-01-11 ($75.75) is not readable. If the identity check fails (unlinked): `PERMNO-88319~1`, `PERMNO-88319` (the 2011 spell) and Yahoo `VC` as three columns, `VC` and `PERMNO-88319` flagged as a possible double. **Take-Two (84761).** A 3-for-2 split on 2005-04-12 is not cut. A trading halt (last row 2002-01-22, next 2002-02-19) makes spell A (1997-04-16 to 2002-01-22) and spell B (2002-02-19 to 2024-12-31). Yahoo `TTWO` starts 2000-01-03, inside spell A, so `TTWO` is spell A before 2000-01-03 (scaled) then Yahoo; spell B is unreadable; nothing is `~1`. **Comverse (10942)** comes out the same way (spell A before 2000-01-03 then Yahoo; the later spell hidden).
  `~k` numbers are assigned in time order within a release; recalibrating a tolerance makes a new release and may renumber, so a run's release id is part of what it means. A link is also refused when CRSP has more than 20 sessions of data after Yahoo's last day (a rename that `ohlcv` does not carry), so the stock does not appear to die and get force-sold; such cases are listed in the load record.
- **Why a separate column per spell, and what the lab does with it.** The engine forward-fills closes (`engine/portfolio.py:199`, `:277`), eligibility counts non-empty closes (`lab/universe.py:238`) and `Bars` has no spell field, so two spells in one column would show a false jump that the engine reads as a return. Each spell therefore has its own column; no engine change. A spell that ends is a series whose data has ended; see 6.7 for what the lab must do with it.
- **Names carry no meaning beyond identity.** `~k` is a spell label, not a trading symbol, and `normalize_yf_ticker` leaves it unchanged.

### 6.2 Where the bars live, and the reader

- **Table.** The CRSP-derived bars go in a new hypertable `market.daily_bars` with wide chunks (about one year) and compression, not into the 7-day-chunk `ohlcv`. `ohlcv` and its `yfinance` rows are not touched; version one never writes into `ohlcv`. Columns: `date` (a `date`: the Parquet files hold midnight timestamps without a time zone, so the importer asserts midnight and converts), `permno`, `spell`, `close`, `abs_prc`, `midpoint_flag`, `load_id`. The always-empty `open`, `high`, `low` and `volume` are not stored; the reader supplies NULL for them, never a fill. Raw `prc`, `ret` and `shrout` stay in `kaggle_crsp.daily`.
- **The close is rescaled.** It is built by chaining `ret` within a spell and anchoring each spell's last day to its last actual price, so a later observation rescales every earlier dollar value. A rule such as "price over $5" must read `abs_prc` (the observed absolute price) and the midpoint flag (a negative `prc` is a bid-ask midpoint), not the close. The file ends 2024-12-31 and has no delisting proceeds, so a last observation is flagged "final observed price", not "delisted".
- **The reader is a function of a release.** `market.ohlcv_daily_combined(release_id, symbols, start, end)` is a plain-SQL function, modeled on `universe.snapshot(p_index, p_load)`, so PostgreSQL can push the symbol and date filters down to the tables. It maps symbols to stocks and spells, applies the visibility rules of 6.1, splices (6.4), merges with `ohlcv`, casts `date` to naive midnight (the only place that cast happens, so no new `timestamp without time zone` column exists on disk) and returns the source of each stock-day. If the timing test (check 8) shows the filters are not pushed down, the fallback is to materialize the combined rows of each release into their own compressed table (extra disk, measured in the pilot).
- **Extra signals travel outside the five bar fields.** `Bars` carries only `open, high, low, close, volume` (`bars.py:328`), so `abs_prc`, the midpoint flag, the source of each day and the "possible double" mark cannot ride in it. They come from the same read as the bars (one function call, one database transaction, so a correction made between two calls cannot desynchronize them; the current reader uses autocommit, so a second call would not be safe). The builder decides how they attach (an optional field on `Bars`, or a second return value); a study that filters on price level uses them, and a run's provenance records the release. `market.stock_spans(release_id, symbol, permno, spell, first_date, last_date, linked)` is a table (one row per spell and release) that lists every stock alive on a date, so a dead-stock study builds its universe from stock numbers and dates without starting from today's survivors.
- **Not two sources for one stock-day, and no switching back.** For a linked stock the combined rows are CRSP only before `first_yf_date`, then `yfinance`. A day `yfinance` is missing inside its own span stays missing (CRSP does not fill it; 401 such interior gaps over 7 days exist across 46 symbols). Rows for the same `(date, symbol)` from two stocks are refused, never merged.

### 6.3 Linking Yahoo symbols to CRSP stocks

Without a link, one company appears twice: as `AAPL` from Yahoo and as `PERMNO-14593` from CRSP. The importer links each `yfinance` symbol to a PERMNO by comparing **daily** returns on shared sessions. A link needs all of:
1. enough shared sessions (or, for a symbol whose whole life before 2025 is shorter, a smaller minimum plus a start-day match; measured: 31 of 1,412 `yfinance` symbols are that short, including 2024 listings such as `GEV`, `SOLV` and `RDDT`). **Start-day match means CRSP's first row is on Yahoo's first day or at most one session after it** (the uploader deleted each stock's first-day row, which carries a letter code; SMCI is Yahoo 2007-03-29 against CRSP 2007-03-30, IBKR 2007-05-04 against 2007-05-07);
2. an agreement measure (correlation, or the share of days whose returns agree within a tolerance) above a calibrated bar, with the first half and the second half of the usable window (split by date) each passing on its own; the written calibration table takes its independently known matches from the McGill dated tickers, and the held-out set from stocks the calibration did not use;
3. the best PERMNO beating the second-best by a margin; and a tie or near-tie is unlinked and reported;
4. no second `yfinance` symbol claiming the same PERMNO (two Yahoo tickers for one company, such as `PX` and `LIN`: the better match gets the link; the other stays unlinked and is reported as a duplicate company).

**No number is fixed in advance.** Earlier drafts said 250 sessions and correlation 0.999. Measured on 15 large stocks (stored Yahoo against CRSP daily returns, 2000 to 2024), only 5 pass 0.999, because the stored Yahoo tape is noisy in 2000 for NYSE names: IBM scores 0.9947 overall (22 of its 26 days that differ by more than 1 point fall in 2000), but 1.0000 for 2005 to 2024 and 0.9859 for 2000 to 2004. So the builder calibrates on a written table of independently known matches and near misses, with a separate held-out set used only to count false matches, starting with a 2005 to 2024 window or a share-of-days measure, and fixes the numbers before the full run. **What a link may and may not do.** A link is a retrospective map: it is proven with Yahoo data from later years, so it is allowed to decide only the column name and the joining of price history. It must never decide which stocks a study may hold on a date. On `combined` bars a study's universe comes from `market.stock_spans` (stock numbers and dates), not from tickers, except for symbols the study names explicitly. Test: changing a later link must not add or remove an investment opportunity on an earlier date. The existing check in `crsp-kaggle/analysis/validate_crsp.py` compares monthly returns for ten stocks and downloads fresh Yahoo prices, so it is only a baseline.

A symbol that fails stays unlinked, is reported as ambiguous with its candidate stocks visible, and stays as two columns (the Yahoo symbol and a placeholder). Those doubles are listed in the load record and flagged in the flags returned with the bars (6.2). Hiding the CRSP side would silently drop history, so it stays visible and flagged. The link is recorded with `source = 'return-match'` and its agreement measure. Nothing is guessed.

### 6.4 Splicing a linked stock

- CRSP closes are anchored to the last day of their spell (2024-12-31 only for spells that reach it) and `yfinance` closes (`auto_adjust=True`) to the date of the last Yahoo refresh, so the two differ by a constant factor per stock (AAPL on 2000-01-03: 0.843029 against 0.837724). `market.daily_bars` is never edited.
- **The scale is computed at read time, not stored (Astra and Fable).** The cache loader overwrites Yahoo history in place, and Yahoo rescales every earlier close at each dividend, so a stored scale goes stale and shows a false jump at the join for every dividend payer. `ref.splice_links(release_id, permno, symbol, first_yf_date, link_day_returns_hash)` stores the link, the join day and a hash of the first K Yahoo **returns** after the join (returns do not change when Yahoo rescales levels); the reader computes `scale = Yahoo close / CRSP close` on the common day **from the same `ohlcv` rows and the same database snapshot** it returns.
- **What drift means, and when it is checked.** A routine dividend refresh changes Yahoo levels but not returns, so it is not drift. Drift is a change in the stored join-window returns. The cheap check (the join-window returns of the linked symbols a read touches) runs on every read and flags "Yahoo input drifted" in provenance; a strict mode refuses to return such data. The expensive check (all linked symbols) runs on demand and when a release is built.
- **Yahoo's first day can move.** `ohlcv` is a cache: 459 symbols "start" 2000-01-03, 247 start 2018-01-02, 174 start 2008-07-30, and the loader can insert earlier rows at any time. The reader therefore uses Yahoo rows only on or after the release's stored `first_yf_date`; if earlier Yahoo rows now exist it flags drift and ignores them; if the join-day Yahoo row has gone it fails with a named error. Demotion of a link to unlinked happens only when a release is built, never at read time, so a pinned release never renames its columns. A Yahoo symbol added to `ohlcv` after a release is read by `combined` as a plain Yahoo column until the next release.
- **The check on the join must not be circular.** The return across the switch equals CRSP's own return that day for any Yahoo price, even one from the wrong company, so checking that day proves nothing. The real test compares Yahoo and CRSP returns over the first K shared sessions after the switch and over later subperiods, on identical session pairs with no gap filling. Because 459 of 1,443 Yahoo symbols start 2000-01-03 and the tape is noisy then (first-60-session correlation is 0.946 for IBM, 0.964 for XOM), a join that lands in 2000 uses a loose, report-only tolerance for the first sessions and the strict test on later periods. A failing link is demoted to unlinked and listed when the release is built.
- **Rules for the edge cases (none occurs in the file today: no null, zero, infinite or <= -100% price or return, so these are guards).** A return of -100% keeps that day as the spell's last row with a "total loss" flag, and the exit rule in 6.7 uses zero recovery for it; a zero or missing price is quarantined; a missing CRSP row on `first_yf_date` means no splice (6.1); a zero or missing Yahoo close on that day means the link is demoted to unlinked and listed.
- An unlinked stock's closes are anchored per spell to its own last price.

### 6.5 One published version per run (releases)

- Every completed import set is published as one **release** row naming the compatible loads (CRSP bars, symbol map, links) and the settings used (gap rule, tolerances). A load that a readable release still depends on cannot be deleted; a release is withdrawn first, and later reads of it raise "release unavailable". Nothing reads "the latest completed load" of a piece on its own; the function resolves everything through one release id in the same read as the bars. `load_bars(source="combined")` accepts a release id and defaults to the newest.
- **`public.ohlcv` is not versioned.** The live cache loader updates rows in place (`ON CONFLICT … DO UPDATE`, `cached_yfinance_loader.py:261`), so an old release cannot rebuild its Yahoo values from `ohlcv`, and a combined result cannot be replayed exactly after a Yahoo refresh until version two keeps an immutable copy of the Yahoo rows (about 6 million rows). Version one fingerprints and flags instead (6.4), and every run records a hash of the exact bars it received (below).
- **Run provenance.** A run records the release id under the key `data_release`, and, for `db` as well as `combined`, a SHA-256 of the exact bars it received (all five fields, all symbols and dates, including SPY). Today a `db` run records only `{"source": "db", "read_only": True}` with no tape hash (`blend.py:122`, `provenance.py:231`), so two `db` runs before and after a Yahoo refresh would compare as the same; a different bars hash must be classified like the existing tape difference even under the same release. The engine's provenance comparison decides whether two results are comparable by classifying how their records differ (`engine/provenance.py`; classes in `_COMPARABLE` are treated as comparable). A different `data_release` must likewise be classified like the tape difference, outside `_COMPARABLE`, so results from different releases are never compared as like with like. The walk-forward writer (`cli_support.py`) and the blend writer (`blend.py:122`) read only snapshot metadata today and must record the release. Tests: replay after a later release is published; replay after a historical Yahoo correction; a Yahoo correction between link time and first read; publish during a read; a query that returns zero bars (a valid result, distinct from "release unavailable", which is the error returned when a withdrawn release is read); the saved JSON and the persisted blend record both carry the release.

### 6.6 Which read path sees the new data (three explicit sources)

`load_bars` and `load_run_bars` get three explicit sources:
- `db`: the Yahoo rows of `public.ohlcv` only, exactly today's database behaviour. **This becomes the default.**
- `combined`: the release-based reader of 6.2. **Opt-in in version one.**
- `snapshot`: the frozen Parquet tape, explicit opt-in.

**The snapshot file named in the manifest (`data/snapshots/ohlcv_20261106.parquet`) is not on disk; only the manifest is.** It was a test fixture for the vectorbt engine rebuild (605 symbols, 2019-03-01 to 2026-10-30), not research data. **Owner position: the snapshot is not needed, and a default pointing at a frozen file is wrong.** Proposed, awaiting approval: the default changes from `snapshot` to `db`. Because `db` keeps today's Yahoo-only database data, the change has no dependency on the import and **lands first, as its own change**. It does change coverage relative to the old default (the snapshot manifest ends 2026-10-30; the database reaches 2026-11-05), so what it guarantees is that the new default equals today's explicit `source="db"` on pinned inputs, not that it equals the old default. Explicit `--snapshot` selection stays for reference runs; a conflicting source and path is an error; `db` runs record the bars hash of 6.5. Adding history to the default read is a separate, later decision, because a window that starts before 2000 would gain early history, change indicator warm-up and the eligibility count (`lab/universe.py:238`), and so change results.

- **Wider than `load_bars`.** `load_run_bars` (`lab/wfo/cli_support.py`) has its own `source="snapshot"` default, and `ggt lab --wfo` and `--blend` both reach it with no `source` argument. `--snapshot <path>` must keep working: today `load_bars` ignores `snapshot_path` when `source="db"` (`bars.py`, near line 306), so with a database default the flag would silently read the database. Rule: an explicit snapshot path selects the snapshot unless another source is also given explicitly.
- **Callers found by search on 2026-11-22** (the builder re-runs the search; the plan lists every hit): scripts `p5_wfo_validation.py`, `p7_live_golden.py`, `p3_pit_parity.py`; tests `tests/data/test_bars.py` (23 `load_bars(` calls pass no `source` and stub the snapshot reader, so they would reach the database: each passes `source="snapshot"`), `tests/lab/wfo/helpers.py`, `test_cli_engine.py`, `test_frozen_evidence_seams.py`, `tests/lab/test_cli.py`, `test_blend.py`, `test_universe.py`, `tests/paper/test_live_golden.py`; research drivers `p2b-evidence/window_convention_check.py`, `p4-evidence/chunker_experiment.py` and `chunker_memory.py`, `p10-evidence/dsr_one_combo.py` (passes the snapshot path positionally), `p5c-evidence/capture_legacy_replica_panel.py` and `compare_ported_replica_panel.py` (already explicit), and the archived `legacy-scripts/p4_strategy_parity.py` and `p5_equity_parity.py`. Each runnable reference check passes `source="snapshot"` explicitly; archived scripts are documented as valid only against their original revision.
- The replica tools have their own fetch path (`lab/data.py`), so "the tools work" holds for everything that goes through `load_bars`.

### 6.7 What the lab can and cannot do with these bars

- **A stock that stops trading must be exited, and today nothing does it.** The engine forward-fills closes, so a position in a spell that ended, or in any of the 21,950 CRSP stocks that end before 2024-12-31, would sit at its last price forever, and a bankruptcy would look like a flat line. The repo has an optional forced-exit helper, `terminal_exits` (`lab/universe.py:278`, "OD7"); only tests call it, and it covers only signal strategies. Rules for `combined` bars:
  - **When a series has ended** comes from the release (`market.stock_spans.last_date`), not from trailing empty cells in the requested window, so two runs with different end dates agree through their common history.
  - **Signal strategies:** the exit fires on the last valid bar and every entry after it is removed (the helper today removes only a same-day entry).
  - **Weight strategies** (a target share per stock, such as `xs_momentum`, through `run_weights`, where an empty weight means "no order" and the closes are forward-filled): the weight is forced to 0.0 on the last valid bar and every later weight is set to "no order". If the builder cannot wire this in for version one, `combined` refuses weight strategies with a clear error instead of running them wrongly.
  - **Proceeds.** The exit fills at the last observed price. That is optimistic (a failed company's holders rarely recover that), and it uses the knowledge that this was the last bar. Every result on `combined` bars says so, and reports sensitivity runs with 0%, 50% and 100% of that value lost on stocks whose data ends for no known successor. A spell that ends in a total loss (6.4) uses zero.
  - Tests: signal and weight cases for a temporary outage, a later order, a total loss, and two runs with different end dates agreeing through their common history; cash, holdings and returns match expected numbers.
  Wiring this in is the one permitted engine-adjacent change; the builder proposes where, and the owner approves if it is in `src`.
- **The 2024-12-31 cliff.** The file ends on 2024-12-31, so every CRSP-only stock freezes that day. Evaluation windows on `combined` bars end on or before 2024-12-31 for any series whose prices come only from CRSP (an old placeholder of a linked stock is CRSP-only; a linked stock's Yahoo column carries on).
- `ggt lab --universe sp500` stops with an error for any date before 1996-01-02, including warm-up (`lab/universe.py`, `membership_mask`).
- The lab picks its symbols from the chosen universe twice (`load_run_bars` and `sleeve_inputs`), and `--universe` accepts only a fixed set of names, so a `PERMNO-<n>` symbol cannot be selected today. Version one does not change the universe choices; the smoke test runs the walk-forward runner on an explicit symbol list, and the builder states how. The lab also needs SPY, so the end-to-end test uses dates where SPY exists.
- With NULL volume the volume-Bollinger voter is silently off (a 5-voter ensemble becomes 4-voter), and with NULL high and low the ATR trailing stop is silently off. Runs on CRSP-only history therefore declare a close-only strategy until other strategies can reject missing inputs. This is recorded as a limit of close-only bars, not fixed.
- **The smoke test checks numbers, not only absence of a crash:** expected eligibility, trades, cash, holdings and returns for a close-only strategy, for a stock with missing fields, for a stock that disappears while a position is open, and for an order submitted after the stock disappeared. A crash found is reported with its location and left unfixed unless the owner asks.

## 7. When information became usable (version-two data)

Each characteristic, fact and trade needs a recorded "first day a trader could have known it" before it feeds any signal. The load records the row's date, the first usable session and the evidence separately. Until a rule is verified for a dataset, that dataset is loaded but not exposed to signals.

- **GKX.** A row dated at the end of month t holds information through the end of month t-1 and is meant to predict month t's return, as the readme's example says; it is usable from the **first trading session of month t**. Waiting until after month t would add a second month of lag. Measured: for AAPL the row dated 2021-01-29 has `mom1m` 0.114574, equal to AAPL's December 2020 return (January 2021 was -0.0055), and the row dated 2021-07-30 has `mvel1` equal to the 2021-06-30 market value. Fable repeated it on 16 stocks and 8,613 stock-months from 1968 to 2021: `mom1m` equals the prior month's CRSP return in 98.7% of rows (the same month in 1.1%), `mvel1` equals the prior month-end market value in 100.0%; annual fields (`agr`, `ep`) change six months after fiscal year-end; quarterly fields change in the January, April, July and October rows for December year-end firms (staler than the readme's four months: AAPL's December 2020 quarter first appears in the July 2021 row); all 647 GKX dates are the last CRSP session of their month. The readme's delays are already in the data and are never applied again. `agr` has the opposite sign to the usual asset-growth definition (AAPL +0.0432 where assets fell 4.32%), so no sign is assumed. Every column type is declared at load (inferred types fail on `datashare.csv`: column 37 is inferred empty, then meets a number).
- **McGill.** Version one stores it raw and uses it only for identity observations (dated tickers) and calibration. Separate inputs from outcome fields (`stock_exret`; `ret_eom` is a date) before any use as features. Its date semantics are unverified: the first CSV row dates both `date` and `ret_eom` to 2000-01-31, while the example program in the folder describes `date` as the first day of the return month, so no McGill feature reaches a signal until each field's date is verified.
- **SEC facts.** The facts file has `adsh, tag, start, end, value` and no unit, `cik` or ticker, and `adsh` is **not unique** in `submissions.csv` (289,381 rows, 289,369 distinct: co-registrant filings share an accession number). So `kaggle_sec.filings` is keyed `(load_id, adsh, cik)` and the join from facts goes through a stated disambiguation rule. `accepted` is a naive Eastern-time string and is parsed explicitly as `America/New_York` (a Pacific session would shift it three hours). Facts are chosen as the latest eligible filing as of the decision time, keeping the original before any amendment. With no unit column, no fact is exposed to signals until a unit source is chosen (default units per tag from the US-GAAP taxonomy, or the SEC's own bulk files, which include units); this is a gate before signal use and does not block loading.
- **Insider trades.** One `date`, no publication time: not exposed to historical signals until the date's meaning is established. The dates run from year 0013 to year 2033 (30 rows before 1990, 9 after 2026-11-22, of 3,469,846), all valid database dates.
- **S&P 500 holdings and daily membership.** Cross-checks only until their effective and publication dates are known. The daily file is a calendar-day expansion (583,510 weekend rows), so any comparison with trading bars filters to trading days.

## 8. How a load works

- A `loads` log (modeled on `universe.loads`) records per load: dataset, Kaggle slug and version, download date, file SHA-256 (matched against `SHA256SUMS`), parser version and options, content hash, row counts, loader git SHA, who and when, and the checks' results. **File identity is separate from load identity:** identical bytes do not stop a corrected parser from making a new load, because the parser version is part of the load's identity.
- Rows carry `load_id`. **Versioning is by whole load, not by row:** a corrected file or parser is a new load, and a reload temporarily doubles that table (hence the pilot in section 3); retention is in section 3.
- A load writes one row per chunk and a final "complete" row. Chunks without a "complete" row are invisible and can be resumed or discarded. A chunk is identified by **(load id, file hash, deterministic chunk key)**, and the parser version is part of the load, so a corrected parser re-reading the same bytes is a new load and a retry can never skip its chunks. A chunk's rows and its log row commit in one transaction; uniqueness is enforced across retries; publication is serialized, and free space is reserved for the next chunk, its indexes, compression and the write-ahead log before it starts. CSV files carry no row count, so a counting pass records it first.
- **Each defect has one outcome.**
  - *Fatal, whole load stops:* hash mismatch; row count differs from the file's metadata; free space below the margin; a missing chunk at publication; a non-zero fractional part in an identifier column.
  - *Row-level, to quarantine with the raw value, file row location and reason:* a date outside the dataset's plausible window (a year-0013 date is a valid database date, so "invalid" cannot mean "unparseable"; the window is set per dataset, for example Form 4 from 1990 to the download date). **A NaN or infinity in a numeric column is not quarantined: the row is kept, the value is stored as NULL and counted.** Each defective row gets exactly one of these outcomes.
  - The check is *parsed rows = accepted (including rows with NULL values) + quarantined*. Identifier columns that arrive as floats because of nulls (`shrcd` and `exchcd` in CRSP are stored as double; `sic2` in GKX has many nulls) are cast to integer or text and refused only if a non-null value has a fractional part. No new `timestamp without time zone` column is created: dates become `date`.
- **Append-only protection.** The strict append-only triggers of the `universe` schema go on the small bookkeeping tables (`loads`, `releases`, `ref.symbol_map`, `ref.splice_links`), where a row is immutable once its load is complete. On the large hypertables a row trigger would block deleting an incomplete chunk and its interaction with compression is unverified, so version one relies on the read-only session `load_bars` already opens plus the load log. (Research sessions log in as the superuser `ggtrader` with a read-only flag; the only other roles are `universe_reader` and `universe_loader`. Separate roles for the new schemas are a version-two step and need the owner's say because they change research credentials.) The builder tests any trigger on one compressed chunk before using it.
